 1. [COMPILER] Calling any first-class function value hangs under --freestanding
================================================================================
 Severity: HIGH    Status: OPEN (worked around)
 Tier:     --freestanding only. Hosted is fine.

 Assigning a top-level function to a `def(...) -> R` variable works, and the
 value can be read back, but CALLING it never returns. The program hangs with
 no fault, no output, no diagnostic.

 Minimal repro (standalone, no toolkit involved):

     def add1(x: int) -> int:
         return x + 1

     @entry
     def kernel_main():
         print("A: direct=" + add1(41).to_str())   # prints "A: direct=42"
         mut f: def(int) -> int = add1
         print("B: fetched")                       # prints
         print("C=" + f(41).to_str())              # NEVER PRINTS -- hangs

 Confirmed identical for all three storage forms:
   - a local variable          `mut f: def(int) -> int = add1`
   - a class field             `o.fn = add1` then `o.fn(41)`
   - a Dict value              `d["k"] = fn` then `mut f = d["k"]; f(e)`
 In the Dict case the store and the fetch both succeed; only the call hangs.
 A no-argument `def() -> void` hangs the same way, so it is not signature- or
 parameter-related.

 Consequence for this project: the proposal's 5.5 handler table
 `Dict[str, def(Event) -> void]` cannot work bare-metal at all.

 Workaround in use: handlers are an interface, not a function pointer.
 `pub interface EventHandler: def handle(self, e: Event) -> void`, with a
 `List[HandlerSlot]` allowlist. Interface dispatch goes through a vtable and
 works on BOTH tiers -- the Canvas backend had already proved that. See
 toolkit/types.tr and toolkit/ui/interp.tr.

 2. [COMPILER] Private recursive method returning `str` hangs under --freestanding
================================================================================
 Severity: MEDIUM  Status: OPEN (worked around)
 Tier:     --freestanding only. Hosted is fine.

 `Interpreter.hit` -- a private (non-pub) recursive method returning `str` --
 hung on Cortex-M. The BYTE-IDENTICAL logic moved to a module-level free
 function runs correctly on both tiers.

 Narrowing evidence:
   - `Interpreter.paint` is also private AND recursive but returns `void`,
     and works fine. So recursion alone is not the trigger.
   - A free function with the same body, same recursion, same `str` return
     works. So the method form is the trigger.
   => the combination (private + recursive + `str` return) is implicated,
      with the string return the most likely culprit.

 Symptom is a silent hang, and it appeared only AFTER a correct render, which
 made it look like memory corruption for a long while.

 Workaround in use: `pub def hit_test(box, x, y, depth) -> str` as a free
 function in toolkit/ui/interp.tr. Guidance: keep recursive, string-returning
 helpers as free functions on the freestanding tier.

 3. [COMPILER] A public function named `register` collides with the C keyword
================================================================================
 Severity: MEDIUM  Status: OPEN (worked around)
 Tier:     both (it is a codegen/name-mangling issue)

 `pub def register(it: Interpreter, name: str, h: EventHandler)` emitted C in
 which the symbol became `_tr_fn_register` AND the interface upcast wrapper was
 silently dropped at the call site. Every other free function in the same file
 correctly emitted `Concrete_as_Interface(x)`.

 Generated C (note the missing OkHandler_as_EventHandler wrapper):

     _tr_fn_register(it, _tr_strz(_tr_str_lit("on_ok")), ok);
     render_to(it, tree, FrameBuffer_as_Canvas(fb));    // correct, for contrast

 The reported error is misleading and points at the wrong argument:

     main.c:150:25: error: passing 'char *' to parameter of
                    incompatible type 'TrStr'

 `register` is a C storage-class keyword, so the mangling is presumably
 deliberate -- but losing the upcast is not, and the diagnostic names the
 string parameter rather than the real problem.

 Workaround in use: renamed to `register_handler`. Guidance: avoid C keywords
 as public function names -- register, auto, extern, inline, restrict,
 volatile, static, signed, union, ...

 4. [SDK] The bump allocator in examples/freestanding/mps2_pure.tr is broken
================================================================================
 Severity: HIGH    Status: OPEN (do not copy the example)

 The shipped example defines:

     @realloc
     def heap_realloc(p: Pointer[u8], n: usize) -> Pointer[u8]:
         return heap_alloc(n)

 It allocates fresh memory and NEVER COPIES THE OLD CONTENTS. That example
 never grows a collection, so the bug is invisible there -- but every
 List/Dict/str append reallocs, so any real program silently loses data.

 Symptom, which is very hard to trace back to the allocator: the parser
 reports `parse: ok` and returns EXACTLY ONE node, holding the LAST line of
 input. Each append discarded everything appended before it.

 Because this is the only bump-allocator example in the docs or the SDK, it
 will be copied. A correct arena needs all four of:

   a) realloc MUST copy the old bytes.
   b) grow IN PLACE when the block is the newest allocation (track _last_ptr).
      Without this, appends are O(n^2) and a 64x48 framebuffer never finishes
      on an emulated Cortex-M3 -- it looks like another hang.
   c) NEVER move _heap_next backwards on a shrinking realloc, or the freed
      tail is handed out while the block is still live. This surfaced as a
      hang inside an unrelated Dict lookup.
   d) NEVER return a zero-length block. A 0-byte request that leaves
      _heap_next unmoved returns the SAME address to the next caller, so two
      live objects share bytes. Round up and enforce a minimum of 8.

 See examples/bare_demo/main.tr for an allocator that satisfies all four.

 Related: `@calloc` in the same example does not zero its memory either,
 which violates calloc semantics and is a latent bug for any caller relying
 on it.

 5. [DOCS] The documented zig cross-compile command does not link
================================================================================
 Severity: MEDIUM  Status: OPEN (documented workaround)

 docs/.../lang/advanced/11_bare_metal.md section "The freestanding compiler"
 gives:

     zig cc -target thumb-freestanding-eabi -mcpu=cortex_m3 -ffreestanding \
         -nostdlib -T build/app.ld -I build/include -o app.elf $(find build -name '*.c')

 Two problems, both fatal:

   a) `-nostdlib` also drops zig's compiler_rt, so every soft-float and 64-bit
      helper the Cortex-M3 lacks fails to link:
        undefined symbol: __aeabi_dsub, __aeabi_dmul, __aeabi_d2iz,
                          __aeabi_i2d, __aeabi_uldivmod, __aeabi_dcmplt, ...
      Use `-nostartfiles` instead: it still omits the C startup files but
      keeps compiler_rt. (The arm-none-eabi-gcc path in the same doc solves
      the same problem with `-lgcc`, so the need is known -- the zig variant
      just has no equivalent.)

   b) zig enables UBSan by default and nothing provides the handlers
      freestanding:
        undefined symbol: __ubsan_handle_add_overflow, ..._type_mismatch_v1,
                          ..._out_of_bounds, ..._divrem_overflow, ...
      Add `-fno-sanitize=undefined`.

 Working command is captured in scripts/build-bare.ps1.

 Note: `ld.lld: warning: cannot find entry symbol _start; not setting start
 address` is EXPECTED and harmless on Cortex-M -- the .isr_vector table drives
 reset. The resulting ELF correctly reports e_machine 40 (ARM), entry 0x0.

 6. [DOCS] `def(...) -> R` as a parameter type is documented as invalid syntax
================================================================================
 Severity: LOW     Status: OPEN (doc is simply wrong)

 docs/.../lang/05_functions.md:477 states:

     def run(f: def(int) -> int) -> void:    # ERROR: not valid syntax
     Fix: Always use `lambda` as the parameter type

 This is wrong. The same document's own "First-Class Functions" section at
 line 893 uses exactly that form and calls it "the idiomatic way to take a
 callback or handler", and the shipped examples/28_first_class_functions.tr
 uses it throughout as a parameter type AND a class field type. Verified
 compiling and running.

 The distinction the doc is missing: `lambda` is the type of CLOSURES;
 `def(...) -> R` is the type of top-level function VALUES. They are different
 things. Line 419 then muddies it further by claiming the two are
 interchangeable, which contradicts line 477 again.

 8. [COMPILER] Upcasting to an interface-typed variable MOVES the object
================================================================================
 Severity: MEDIUM  Status: OPEN (worked around); may be by design
 Tier:     both

 Three related behaviours that are individually defensible but collectively a
 trap, because the docs recommend the one form that breaks:

   a) `mut view: Canvas = canvas` MOVES `canvas`. Afterwards
      `canvas.save_ppm(...)` is `[M-1] 'canvas' was moved`. The interfaces doc
      presents this explicit upcast as the recommended style.
   b) A METHOD call does not auto-upcast at all: `it.render(tree, canvas)`
      fails to compile with
        passing 'BufferCanvas *' to parameter of incompatible type 'Canvas_obj'
   c) A FREE FUNCTION call does auto-upcast, and does NOT move:
      `draw(canvas)` where `def draw(c: Canvas)` leaves `canvas` fully usable.

 So the only way to pass a concrete object to interface-typed code and still
 own it afterwards is a free-function wrapper. That is why
 toolkit/ui/interp.tr has `render_to()` and `register_handler()` -- both exist
 purely to route an upcast through a free function.

 Also relevant: assigning a local into a FIELD moves it. `self.root = box`
 then `self.paint(box, ...)` is `[M-1]`; assign first, then work through the
 field.

 9. [COMPILER] `match` on an enum needs a redundant `case _:` or [F-3] fires
================================================================================
 Severity: LOW     Status: OPEN (worked around)
 Tier:     both

 A `match` that lists every variant of an enum and returns in every arm is
 still reported as
     [F-3] Missing return on code path
 unless a trailing wildcard `case _:` is added. The wildcard is unreachable;
 the return-path checker just cannot see exhaustiveness.

 Workaround: always add a trailing `case _:`. Every match in toolkit/ui/ast.tr
 carries one for this reason.

 12. [COMPILER] tauraro_rt.h treats bare _WIN32 as "real hosted Windows"
================================================================================
 Severity: MEDIUM  Status: OPEN (worked around)
 Tier:     --freestanding, on any target whose C compiler predefines _WIN32
           for ABI-compatibility reasons without actually being hosted Windows
           (confirmed: zig's `-target x86_64-uefi`)

 UEFI genuinely shares the Microsoft x64 calling convention and PE/COFF
 executable format, so zig's `x86_64-uefi` target predefines `_WIN32`,
 `_WIN64`, and `_MSC_VER` -- a deliberate, correct choice on zig's part, not
 a zig bug. Confirmed with:

     zig cc -target x86_64-uefi -dM -E some.c | grep _WIN32
     #define _WIN32 1
     #define _WIN64 1
     #define _MSC_VER 1933

 `tauraro_rt.h` uses bare `#ifdef _WIN32` (not `#if defined(_WIN32) &&
 !defined(TAURARO_KERNEL)`) to gate a block of Windows-hosted-only code:
 `#include <windows.h>`, `#include <psapi.h>`, `#include <bcrypt.h>`, and
 calls to `_putenv_s`. None of that exists on a real UEFI target, so a
 `--freestanding` build for `x86_64-uefi` fails with:

     tauraro_rt.h:1069:10: error: 'windows.h' file not found
     tauraro_rt.h:864:76: error: call to undeclared function '_putenv_s'

 despite `#define TAURARO_KERNEL` already being active in the same
 translation unit (`--freestanding` always emits it) -- which is exactly the
 signal that should have suppressed this block. The header's own comment
 elsewhere states `TAURARO_KERNEL` reduces the runtime to "single-threaded,
 no-OS, no-socket code that any bare toolchain accepts"; the `_WIN32` branch
 is the one place that promise does not hold.

 Workaround in use: undefine the three macros before the generated C is
 compiled, in `scripts/build-uefi.ps1`:

     zig build-exe ... -cflags -U_WIN32 -U_WIN64 -U_MSC_VER -- <generated .c files> ...

 Note `zig build-exe` does NOT accept `-U...` as a bare top-level flag (it
 is rejected as "unrecognized parameter") -- it must be bracketed with
 `-cflags ... --` immediately before the `.c` sources it should apply to,
 and does not apply to any `.zig` source passed outside that bracket.

 13. [COMPILER?] Certain specific RGB int values hang on --freestanding Cortex-M
================================================================================
 Severity: MEDIUM  Status: OPEN (root cause NOT found; worked around by avoiding
                   the trigger values)
 Tier:     --freestanding thumb-freestanding-eabi / cortex_m3 only. Confirmed
           NOT present hosted, and NOT present on the UEFI x86_64 target --
           the same amber/violet colors render correctly there.

 Filling an entire canvas with certain 24-bit packed-RGB int color values,
 then converting each pixel back to R/G/B via `(c/65536)%256` etc. and
 emitting the string with StringBuilder + print(), hangs deterministically --
 every time, same value, same result -- partway through the FIRST row. No
 fault message, no further UART output, ever (waited 4+ minutes on one run).

 Reduced to a ~110-line standalone repro with its own bump allocator, no
 toolkit code at all: FrameBuffer.init(96,56,0) + FrameBuffer.fill_rect(whole
 canvas, color) + a row-emission loop matching
 toolkit/render/bare/framebuffer.tr's emit_ppm exactly. Confirmed present
 whether emit_ppm is a method, a free function, or manually inlined in
 main() -- rules out method-dispatch/self-parameter theories. Confirmed NOT
 about cumulative heap usage: growth is perfectly linear (~2.4KB/row) with no
 spike, and reducing per-row allocation to near-zero (reusing one
 StringBuilder via .clear() instead of allocating fresh per row) did not
 change WHICH row it hung on even though it drastically cut memory pressure --
 ruling out the heap-exhaustion theory this entry originally suspected.

 Bisection (R,G,B as 0-255 ints, packed 0xRRGGBB), holding two channels fixed
 and sweeping the third:

     0xEF4444 (239,68,68)    WORKS   -- the demo's plain "red"
     0xF59E0B (245,158,11)   HANGS   -- the demo's "amber"
     0x8B5CF6 (139,92,246)   HANGS   -- the demo's "violet"
     0xF54444 (245,68,68)    WORKS   -- amber's R alone: fine
     0xEF9E44 (239,158,68)   WORKS   -- amber's R+G, "normal" B: fine
     0x009E0B (0,158,11)     WORKS   -- amber's G+B, R=0: fine
     0xEF0000 / 0x00009E     WORKS   -- R alone / B alone: fine
     0xEF9E0B (239,158,11)   HANGS   -- amber's R+G+B together: hangs
     0xEF9E09 (239,158,9)    WORKS   -- B one less
     0xEF9E0A (239,158,10)   HANGS   -- B one MORE -- adjacent ints, opposite result
     0xEF9E0C / 0xEF9E10     HANGS   -- B=12, B=16: also hang

 So: no single channel triggers it. No two-channel combination we tried
 triggers it. All three channels together, in specific ranges, do -- and the
 boundary is sharp enough that incrementing B by exactly 1 (10 vs 9) flips
 hang vs. work, while a LARGER packed integer value (0xEF9E44 = 15,692,868)
 works fine and a SMALLER one (0xEF9E0A = 15,691,786) hangs -- ruling out a
 simple magnitude/overflow threshold on the packed int itself.

 Given the hang survives free-function extraction, inlining, interface
 removal, and drastic allocation reduction, the remaining suspects are: (a) a
 genuine codegen bug in `--freestanding` int-to-string/division-remainder
 lowering for specific bit patterns on this target, or (b) something in the
 zig-emitted Cortex-M3 startup/runtime for this exact toolchain combination
 (thumb-freestanding-eabi, `-mcpu=cortex_m3`, compiler_rt soft-division
 routines). Not narrowed further than that -- doing so would need disassembly
 of the generated code around the failing append_int/division call, which
 was not done.

 Workaround in use: `examples/bare_demo/main.tr`'s UI now uses only colors
 confirmed safe this session (red, green, blue, slate background, white text)
 and avoids amber/violet/mist entirely. If a bare-metal demo needs a color
 outside that set, bisect it the same way before trusting it.

 IMPORTANT ADDENDUM -- this is not purely a per-color-value bug:

 - Two independently-safe colors placed side by side WITHIN THE SAME ROW
   (e.g. a "grow" panel + a fixed-width panel in one flex-row, each a
   confirmed-safe color alone) can ALSO hang -- reproduced with
   fill_rect(0,0,80,56,blue) + fill_rect(80,0,16,56,red) on an otherwise
   identical harness, both colors individually confirmed safe uniform-filled.
 - CANVAS WIDTH matters independent of color: the exact same UI, same
   colors, same everything else, hangs at width=96 and completes cleanly at
   width=88. This was found only because the actual demo (mixed red/blue in
   the button row, at width=96) still hung after switching off amber/violet/
   mist entirely -- narrowing to "just shrink the canvas a little" fixed it
   without needing to explain why.

 Net effect: SEVERAL independent variables interact (specific packed color
 values, multiple colors in one row, and canvas width), and none alone
 fully explains the failure. The pragmatic rule until this gets a real root
 cause: after ANY change to a bare-metal demo's colors OR canvas dimensions,
 re-run it under QEMU and confirm it actually completes (`scripts/run-bare.
 ps1` reports truncated row counts on a hang) -- do not assume a change is
 safe just because the individual pieces were separately verified before.


================================================================================
 NON-BUGS -- environment gotchas, recorded to avoid re-diagnosis
================================================================================

 - tauraroc is on the USER PATH (HKCU:\Environment). A shell started before
   installation reports "not recognized". Refresh from the registry rather
   than concluding it is missing.

 - Module resolution checks the CWD first, so `toolkit.*` paths only resolve
   when compiling from the repository root.

 - The first compile is slow: zig builds its target libc once, then caches.
   A 2-minute timeout looks like a hang on a cold cache.

 - PowerShell 5.1: do not redirect a native tool's stderr with `2>&1`. Each
   line comes back as an ErrorRecord and trips ErrorActionPreference=Stop even
   when the tool exited 0 having emitted only warnings. scripts/build-bare.ps1
   redirects through `cmd /c` for this reason.

 - `zig cc` needs `-mcpu=cortex_m3` as a single token; passing `-mcpu` and the
   value as separate arguments yields "Unknown Clang option: '-mcpu'".

 - qemu-system-arm is installed at "C:\Program Files\qemu" and is NOT added to
   PATH by the installer.

 - The bare demo never halts (there is no OS to exit to), so qemu must be
   killed by a timeout. Exit code 124 from `timeout` is the expected success
   signal, not a failure.
